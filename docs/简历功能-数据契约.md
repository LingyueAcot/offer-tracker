## 一、表结构：新增 `resumes`（`schema.py` 只加不改）

```sql
CREATE TABLE IF NOT EXISTS resumes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    title       TEXT NOT NULL DEFAULT '未命名简历',   -- 多份简历的区分名（决策 #2）
    is_default  INTEGER DEFAULT 0,                    -- 1 = 打开时的默认那份
    sort_order  INTEGER DEFAULT 500,                  -- 列表排序（与 notes/stages 同风格）
    content     TEXT DEFAULT '',                      -- JSON：结构化正文（见第三节）
    layout      TEXT DEFAULT '',                      -- JSON：模板/字号/边距（见第四节）
    content_ver INTEGER DEFAULT 1,                    -- content JSON 的格式版本
    rev         INTEGER DEFAULT 1,                    -- 乐观并发版本（每次成功保存 +1）
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
)
```

**要点**

- **正文与排版分开存**（`content` / `layout` 两个列）：这是方案明确要求——
  换模板、调字号不该碰正文，也不会因为一处改动把整份内容重写。
- **多份简历** = 表里多行；`is_default` 只允许一份为 1（服务层保证，不加 DB 约束，避免老库冲突）。
- **`created_at` / `updated_at` 为 NOT NULL**：与既有表的写法一致（`notes` / `applications` 都是这样）。
- **不新增任何指向 `applications` 的外键**（决策 #2：暂不关联投递记录）——
  将来要关联时属于新需求，届时按"只加不改"补列。

**`SCHEMA_VERSION`：1 → 2**（`server.py`）。按该常量的注释约定，只有 `schema.py` 真的改了结构才动它。

> ⚠️ 已知既存行为（本次**不**改）：`meta.schema_version` 用 `INSERT OR IGNORE` 写入，
> 所以**老库升级后仍显示旧版本号**，只有新建库写新值。表结构的补齐靠
> `CREATE TABLE IF NOT EXISTS` 完成，与这个显示值无关。这属于既有设计，不在本功能范围内动它。

## 二、条目标识与顺序（"数组顺序和条目标识稳定"）

- 每个条目带**稳定的字符串 id**：`edu_1` / `work_2` / `proj_1` / `skill_3` …
  由服务层在新建条目时生成（`<前缀>_<自增序号>`，在**该简历内**唯一）。
- **数组顺序即显示顺序**：不另设 `sort_order` 字段，避免两处真相。
- 服务层保存时校验：同类数组内 id 必须唯一；缺失 id 的条目补一个（不报错，容错向内）。

## 三、`content` JSON 格式（`content_ver = 1`）

借鉴 `resume-schema` 的字段子集，**只取本项目模板真正用得到的部分**（钉定提交见来源清单）：

```json
{
  "basics": {
    "name": "", "headline": "", "phone": "", "email": "",
    "gender": "", "location": "", "political": "",
    "ethnicity": "", "hometown": "", "education_level": ""
  },
  "education": [{ "id": "edu_1", "school": "", "degree": "", "major": "",
                  "start": "", "end": "", "bullets": [""] }],
  "work":      [{ "id": "work_1", "org": "", "role": "", "start": "", "end": "",
                  "bullets": [""] }],
  "military":  [{ "id": "mil_1",  "org": "", "role": "", "start": "", "end": "",
                  "bullets": [""] }],
  "campus":    [{ "id": "cam_1",  "org": "", "role": "", "start": "", "end": "",
                  "bullets": [""] }],
  "projects":  [{ "id": "proj_1", "name": "", "role": "", "start": "", "end": "",
                  "topic": "",
                  "sections": [{ "label": "", "text": "" }] }],
  "skills":    [{ "id": "skill_1", "text": "" }],
  "awards":    [{ "id": "award_1", "text": "" }]
}
```

- 七个板块与用户模板的左/右栏一一对应：教育 / 技能 / 荣誉（左），部队 / 项目 / 实习 / 在校（右）。
- `projects[].sections[].label` 对应模板里的「材料合成 / 表征分析 / 性能测试 / 成果产出」这类小标题，
  用**数据驱动**而不是写死四个标签，方便用户增删。
- `skills` / `awards` 是纯文本条目（模板里就是「• 一句话」）。
- **v1 不做照片**：模板的照片框保持空白（`layout.show_photo = false`）。
  真要做照片涉及二进制存储与打包体积，属于新需求。

## 四、`layout` JSON 格式（`content_ver` 之外单独版本化，当前 `1`）

```json
{
  "template": "two-column-private",
  "font_scale": 1.0,
  "line_height": 1.55,
  "page": { "margin_top_mm": 0, "margin_left_mm": 0 },
  "section_order": {
    "left":  ["education", "skills", "awards"],
    "right": ["military", "projects", "work", "campus"]
  },
  "section_titles": { "work": "实习经历" },
  "hidden_sections": [],
  "theme": {
    "header_bg":   "#3B5F82",
    "header_text": "#FFFFFF",
    "accent":      "#2F6595"
  },
  "show_photo": false,
  "max_pages": 2
}
```

- `template` 目前只有一个值（用户给的「私企两栏版」）。留这个键是为了将来加模板时**不用改表**。
- `page.margin_*` 与模板几何对齐（模板本身是 A4 满版、零页边距，内容自带内缩）。
- `max_pages` 配合决策 #3「一页优先、允许多页」：超出时提示分页，不静默截断。
- **`section_titles`（2026-10-10 加）**：板块标题可改名（如 `部队经历` → `服役经历`）。
  只认已知板块键；空标题当没改。缺键用内置标题。
- **`hidden_sections`（2026-10-10 加）**：不显示的板块（如没有部队经历就藏起来）。
  只接受已知板块键；隐藏只影响**渲染与导出**，数据仍在 `content` 里没丢。
- **`theme`（2026-10-10 加）**：配色。三个值都必须是 `#RRGGBB`，非法值保留默认。
  **默认值取自己用户那份 PPTX 原件的实测值**（`tools` 里的一次性提取脚本，
  抬头 `#3B5F82` / 抬头文字 `#FFFFFF` / 板块标题与分隔线 `#2F6595`）。
  页面上用三个取色器改，改完立刻反映到右侧预览。
- **铺满与均化间隔**：两栏高度 = `297mm − 47.1mm`（页面减抬头），
  板块之间插入弹性间隔元素（`flex:1 1 auto`）——**剩余空间被均匀分给各板块之间**；
  内容变多时间隔先压到 0，不会把内容挤出纸面（溢出仍由 `rz-metrics` 报出来）。

## 五、校验与长度限制（**在 `services/` 层做**，`core/` 不许碰 json）

| 项 | 规则 | 违反时 |
|---|---|---|
| `title` | ≤ 60 字符，去首尾空白；空则回落「未命名简历」 | 自动修正 |
| 每个数组 | ≤ 30 条 | 400，指出板块名 |
| 每条 `bullets` | ≤ 12 条；单条 ≤ 500 字符 | 400 |
| `basics` 各字段 | ≤ 200 字符 | 400 |
| `sections` | ≤ 8 个/项目；`label` ≤ 20、`text` ≤ 1000 字符 | 400 |
| `content` / `layout` 序列化后 | 各自 ≤ 256 KB | 400（防把库撑爆） |
| 未知键 | **忽略**（向前兼容，不报错） | 静默丢弃 |
| 类型不符 | 400，响应里带 `field` 路径（如 `education[2].start`） | 400 |
| 日期 | 不解析，原样存字符串（用户怎么写就怎么留） | —— |
| 数字类（`font_scale`） | 0.8 – 1.4；`line_height` 1.2 – 2.0 | 400 |

## 六、并发保存冲突规则（"过期版本保存拒绝覆盖"）

1. `GET /api/resumes/<id>` 返回 `rev`。
2. `PUT /api/resumes/<id>` **必须带 `rev`**：
   - `rev` 与服务端相等 → 保存成功，`rev + 1`，写 `log_change`；
   - 不相等 → **409**，响应带服务端当前 `rev` / `updated_at`，**一个字都不写**。
3. 无 `rev`（旧客户端/手写请求）→ 400，要求带上。
4. 前端收到 409：提示「这份简历在别处被改过」，让用户选「用我的覆盖」或「放弃我的修改」——
   显式选择后才允许用服务端最新 `rev` 重试，避免静默覆盖。

> 与项目既有风格一致：所有写操作都要 `log_change(...)`（含删除前的完整数据）。

## 七、接口清单（新增 `app/api/resumes.py`，遵循 `api/` 的 mixin 模式）

| 方法 | 路径 | 作用 | 备注 |
|---|---|---|---|
| GET | `/api/resumes` | 列表：id / title / is_default / sort_order / rev / updated_at | **不带 content**，省流量 |
| GET | `/api/resumes/<id>` | 单份完整：content + layout + rev | |
| POST | `/api/resumes` | 新建（可带 title / 从 `layout` 默认值起） | 首次创建自动设为默认 |
| PUT | `/api/resumes/<id>` | 保存（body 含 rev） | 409 冲突见第六节 |
| DELETE | `/api/resumes/<id>` | 删除 | 写审计（含删除前数据） |
| POST | `/api/resumes/<id>/duplicate` | **复制**（决策 #2） | 复制 content+layout，title 加「副本」 |
| POST | `/api/resumes/<id>/default` | 设为默认 | 同时清掉其他行的 is_default |

## 八、PDF 导出怎么走（不新增后端接口）

- **主路径（已实测可用）**：在前端给简历预览加打印样式，遮住外壳与侧栏，然后 `window.print()`。
  实测：应用外壳里 `window.print()` 会**模态阻塞**（打印预览确实打开），用户选「另存为 PDF」。
- **退路（已实测可用）**：新增一个**只渲染简历**的 URL（例如 `/?print=1&resume=<id>`），
  用本地浏览器打开再 Ctrl+P。走的是同一套 Chromium 打印引擎，产出 A4 文字型 PDF（已验：
  209.9×297.0mm、嵌入字体、无位图）。
- **不做**：`CoreWebView2.PrintToPdfAsync`（无对话框直出）虽然存在，但**只能从 UI 线程访问**，
  本次不引入这条路（探针证据见 `开发记录`）。
