## 五、架构

```
桌面快捷方式
    │
    ▼
pythonw.exe launcher.py          ← 外壳宿主（常驻，等于窗口）
    │
    ├─ 1. 单实例检查（命名互斥体；已开则把现有窗口提到前面）
    ├─ 2. 探测端口 → 没有服务就用 pythonw 起 server.py
    ├─ 3. 先开启动画面（本地 splash.html，秒开，不白屏）
    ├─ 4. 等 data/runtime.json 出现 → 加载 http://127.0.0.1:<实际端口>/
    ├─ 5. 加载完成后打 Win32 补丁：拖动 / 8 向缩放 / 圆角 / 阴影
    └─ 6. 窗口关闭 → 通知 server 优雅退出 → 自己退出

server.py                        ← 后端（照旧：数据 + 接口 + 宣讲会同步）
    └─ 心跳与看门狗保留，作为外壳异常时的兜底
```

### 窗口控制走哪条通道

用 **pywebview 的 `js_api` 桥**，页面里只暴露一层薄封装：

```js
window.addEventListener('pywebviewready', function () { Shell.bind(window.pywebview.api); });
Shell.minimize();  Shell.toggleMaximize();  Shell.close();  Shell.startDrag();
```

理由：这样 `server.py` 不用加任何接口（保持"一行不动"），前端也只有一个 `Shell` 对象要记。在普通浏览器里打开时 `Shell.available()` 返回 false，标题栏上的窗口按钮自动隐藏，页面退化成现在这个样子——`work/` 下那套自检脚本（用无界面 Chrome 跑的）因此不受影响。

### 退出链路（要重新串一遍）

| 场景 | 现在的行为 | v3 的行为 |
| --- | --- | --- |
| 关窗口 | 页面发 closing → 服务等 15 秒 → 退出 | 窗口关闭事件 → 主动通知服务退出（更可靠） |
| 刷新页面 | 不许误退（有宽限期） | 刷新根本不会关窗口，天然满足 |
| 同步宣讲会跑一半 | `busy` 计数 > 0 时不退 | 保留同样的保护 |
| 双击两次图标 | **会开第二个窗口**（现存小毛病） | 命名互斥体 → 把已有窗口提到前面 |

### 6.3 必须注意的坑

视图状态存在 localStorage 里。如果上次退出时停在时间链，删掉之后打开会是一片空白。

`if(initialView === "dash" || initialView === "board" || initialView === "snake" ...)` 这个白名单校验就是处理这种情况的——去掉 `"snake"` 之后它会回退到首页。改完必须用 `#snake` 直接访问一次，确认不白屏。

### 6.4 自检脚本（这里有个会误伤的坑）

`work/verify_desktop.js` 不能直接改成「确认时间链已移除」——**2.0 还保留着时间链，那样改会让 2.0 的检查永远失败**。

做法：把端口和「期望有/没有时间链」都做成参数，两个版本共用一份脚本。

| 脚本 | 现在 | 改成 |
| --- | --- | --- |
| `verify_desktop.js` | `const BASE = "http://127.0.0.1:8766/"` 写死 | 读命令行参数，默认 8766；时间链那一项按参数决定是「有节点」还是「已移除」 |
| `test_desktop.py` | `BASE = "http://127.0.0.1:8766"` 写死 | 同样读参数，默认 8766 |

### 阶段 3 · 无边框与窗口行为（技术核心）

- `frameless=True`，然后用 Win32 补齐系统原本免费提供的能力：
  - 拖动：`ReleaseCapture()` + `SendMessageW(hwnd, WM_NCLBUTTONDOWN, HTCAPTION, 0)`，拿到原生拖动、边缘吸附、Aero Snap
  - 8 向缩放：自己处理 `WM_NCHITTEST`，按缩放后的 8px 边缘映射 HT 值
  - 双击标题栏最大化 / 还原
  - 圆角与阴影：DWM 属性 33 + `WS_THICKFRAME`
  - 高 DPI：边缘热区按 `GetDpiForWindow` 换算，不能写死像素
- **验收**：六项手工过一遍；在 125% / 150% 缩放下边缘热区仍然对得上；最大化后拖回可还原。
- **回退**：`window_mode` 改回 `"app"`；右下角 gripper 方案作为备选（拖右下角调用 `resize()`），代价是没有边缘吸附。

#### 阶段 3 + 4 完成记录（2026-09-20）

这两段是一起做的——无边框窗口如果不同时给标题栏，窗口就没法拖，等于不可用。
最终形态：**无边框 + 自绘标题栏**（`📮 应届海投 | 搜索框 | 导出 ＋新增投递 | ─ □ ✕`），
原来的整条 sticky 顶栏并进了标题栏，等于白赚约 50px 内容高度。

**这一段踩了 5 个坑，全都记下来（前 4 个都靠探测脚本或日志定位）：**

| 坑 | 症状 | 事实与解法 |
| --- | --- | --- |
| pywebview 自带 `easy_drag` | 拖动后窗口"黏着"鼠标 | 弃用，自己做拖动 |
| 原生 `ReleaseCapture + SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)` | **窗口假死**（鼠标转圈、点不动） | Windows 会进入"等鼠标松开"的模态循环，而调用不是从 GUI 线程发起的，松开事件进不去 → 永远等。整条路线删除 |
| **pywebview 的 `js_api` 桥** | 按钮和拖动**全部静默失效** | 在「先显示启动画面、再 `load_url` 切真实页面」这个流程下，切过去之后页面里根本没有 `window.pywebview`。**改成 HTTP 控制通道**：启动器开一个随机端口的这台电脑服务，端口通过 `&shport=` 写进页面地址，页面用 `fetch` 发命令 |
| **启动流程用 `urllib` 做健康检查** | **启动卡死**，窗口一直停在启动画面 | 这台机器上连这台电脑环回端口都会被静默丢弃（实测：端口没人监听时是 **timeout 而不是 connection refused**）。`urllib` 要过代理探测/DNS/opener 一堆环节，卡住风险实打实。**换成裸 socket + 线程硬超时**，从结构上保证启动流程不会被网络请求拖住 |
| 页面动作名与启动器协议不一致 | 点 X 毫无反应，只表现为日志一句「收到不认识的窗口命令：close_window」 | 页面发 `close_window`、启动器只认 `close`。跨语言的字符串约定没有编译期检查，**加了一条静态一致性检查**（见下） |

**这一阶段新增的自检**（`work/verify_shell.js`，17 项）：

- 普通浏览器路径下**不该**有标题栏；外壳模式（`?shell=borderless`）下**必须**有 —— 两件事分开验，互相不干扰
- 顶栏里三个元素确实被搬进标题栏（比位置，不是只看存在）
- 窗口按钮是 SVG 而不是字符图标（字符图标来自不同字库，大小对不齐 —— 用户反馈过）
- 带 / 不带 `&shport` 两种情况：不带时页面要给出可见提示
- **静态一致性检查**：抓出 `index.html` 里所有 `shSend("...")` 的动作名，和 `launcher.py` 里 `handle()` 认的名字比对，对不上就报错

> 顺带修了自检脚本自己的一个 bug：有一条检查用「搜提示文字」判断，而页面脚本源码里就写着那句话
>（`dump-dom` 会把 `<script>` 内容也带出来），所以**永远命中、白测一场**。改成检查渲染出来的
> 元素属性 `id="sh-warn"`。假通过的检查比没有检查更糟。

| 风险 | 应对 |
